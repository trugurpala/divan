# v0.17.0 target — One Divan / Modular Engine

## Mandate

Keep Divan as one product and one repository; make Hükümdar the explicit final
authority; establish a modular, first-party engine without external runtime
dependency; preserve existing users; and publish only after code, compatibility,
documentation, CI, and live release evidence agree.

## Product outcome

A user can inspect the system with:

```powershell
python scripts/divan.py architecture --json
```

The result must show one product (`divan`), nine validated modules, the ordered
authority chain beginning with `owner/Hükümdar`, and the invariant that the core
has no external runtime dependency.

## In scope

- Canonical `plugins/sadrazam/divan_runtime/` package with relative imports.
- Machine-readable module graph and bilingual authority contract.
- Canonical `architecture` and `validate` commands.
- Legacy `company` Python/JSON paths and `company-validate` alias.
- Deterministic packaged runner using `divan_runtime.cli`.
- ADR, plan, README, canonical guides, Wiki, site, changelog, blueprint,
  progress, impact graph, quality configuration, and release manifest.
- Characterization, failure, runner reproducibility, full verification,
  independent review, PR/CI, merge, tag, Release, Pages, and Wiki readback.

## Explicitly out of scope

- Merging PR #28 or PR #29 without a separate, current architectural review.
- Promoting the 64-commit Nizâm-ı Sefer branch or its temporary evidence files.
- Renaming stable `.divan/`, DCS/DPS, receipt, install-state, or provider ids.
- Adding a daemon, hosted control plane, LangGraph, OpenHands, or another
  repository as a runtime dependency.
- Claiming v1 completion without independent non-owner evidence for issue #34.

## Acceptance criteria

1. `architecture --json` is deterministic and rejects malformed, missing,
   duplicate, cyclic, or authority-expanding contracts.
2. Only `owner` may expand scope; every other authority row is delegated in
   canonical order. Public CLI mutation binds exact arguments to a deterministic
   mandate id, rejects delegated actors, and states that host permissions—not
   Divan—provide identity authentication.
3. Canonical and legacy `validate` paths produce identical JSON and exit codes.
4. Runtime and legacy contract JSON files are byte-identical.
5. Existing inspect, plan, impact, init, project, goal, receipt, adoption,
   audit, verify, and release behavior remains characterized.
6. Two project-runner builds from one clean commit are byte-identical; the
   archive carries the canonical package, source envelope, and SEO policy.
7. Ruff, mypy, Clean Code, coverage, repository validation, Wiki, handoff,
   release checks, full tests, and `git diff --check` pass.
8. An independent reviewer reports no open blocking finding.
9. PR checks are green and branch protection is not bypassed.
10. v0.17.0 tag, non-draft GitHub Release, five verified assets, checksums,
    attestations, Pages, and Wiki all bind to the merged release commit.

## Rollback

Before merge, drop the focused branch. After merge but before tag, revert the
single v0.17 PR. After publication, never move the tag: publish a corrective
patch release. Legacy paths remain present, so consumers can stay on the
compatibility surface during rollback.
